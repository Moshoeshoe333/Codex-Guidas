# CG-044 — Separate static workspaces do not prove shared-state workflow integrity

- **Status:** Derived
- **Date discovered:** 2026-11-25
- **Last reviewed:** 2026-11-25
- **Source project:** ScoutSA
- **Source artifact/path:** `prototype/README.md`, sections “Guided Demo Journey”, “Open the prototype” and “Explicit limitations”
- **Commit / CI run / issue:** Exact head `125c48082633ec4bb744f5734b78cc659441e8ba`; hosted workflow #1087, run `45606385341`
- **Severity and rationale:** Medium — navigation between pages can be mistaken for persistence, synchronization or a single end-to-end transaction.
- **Applicability:** General

## Event
The ScoutSA prototype README explicitly describes the guided journey as six separate static workspaces, not one shared-state transaction or production workflow. It separately describes JSON handoff as a manual file exchange rather than shared application state, persistence, authentication, authorization, API synchronization or production integration.

## Expected behaviour
A product or test report should state exactly which continuity mechanism exists: navigation only, in-memory state, explicit file handoff, local persistence, API synchronization or durable transactional storage.

## Actual behaviour
The prototype provides separate static pages and a synthetic, versioned JSON handoff for bounded exchange. The documented limitations expressly deny shared application state and production integration.

## Impact
Readers and testers can infer persistence or workflow continuity from a smooth demonstration even when the underlying pages are isolated or require manual handoff.

## Root cause
Architectural boundary, not a confirmed defect: a visual journey can span multiple pages without those pages sharing state or participating in one transaction.

## Corrective action
Describe the handoff and state boundary beside the workflow. Test import/export validation, identity matching, rollback and replay separately from page navigation.

## Preventive / detective control
Every multi-screen demo should include a state-continuity statement: what is shared, what is copied, what is session-only, what is manually transferred, and what is not implemented. Acceptance criteria must not infer durable state from navigation success.
