# Doctrines — Philosophy into Practice

These documents state the principles that guide how we reason, build, allocate effort and treat people. A doctrine is a decision aid, not proof that a project complies with it.

- [Tri-Tier 33 — Mind, Body and Spirit](tri-tier-33/README.md) — proposed technical integrity instrument for code, persistence, UI and their seams (v0.3.0-draft; not ratified), including the 99-tier Harmony crosswalk.
## Core doctrines

- [33-Tier Epistemological Framework](33-tier-framework.md) — how we distinguish purpose, knowledge, evidence and permission.
- [33-Perspective Master Register](33-perspective-master-register.md) — 33 operational lenses; version 0.2 includes five refinements and remains proposed.
- [Three-Project Case-Study Review](case-studies/2026-11-18-three-project-register-review.md) — comparative desk reviews of ScoutSA, SoulSyncMobile and Mall Navigre, with evidence limits.
- [Grassroots Contextual Engineering](scoutsa-doctrine.md) — how we design around real human, community and resource constraints.
- [Sustainable Portfolio Ecology](portfolio-ecology.md) — how we balance creation, livelihood, focus and preservation.
- [Honesty Without Malice](honesty-without-malice.md) — how we communicate, record uncertainty and learn from failure.

## Use and governance

Each doctrine carries a maturity label: **Proposed**, **Adopted working principle**, or **Verified control**. A value statement is not automatically an implemented control. Translate relevant principles into project requirements, tests, operational procedures and evidence. Review doctrines when reality or capacity changes; preserve the prior rationale rather than silently rewriting history.
